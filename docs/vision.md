# Система работы веломастерской Vella — общая концепция

Статус: черновик v0.1 · Дата: 2026-09-09 · Владелец: старший механик

## 1. Зачем это

Сейчас в мастерской нет единого стандарта: цены и правила мастера задают сами,
учёта работ и времени нет, знания не передаются новичкам. Цель — построить
систему работы мастерской, в которой:

- любой новый мастер берёт технологическую карту и работает по ней с первого дня;
- каждая работа на велосипеде фиксируется: что делали, сколько заняло, какие
  запчасти и расходники ушли;
- при приёмке фиксируется клиент и запрос, затем делается диагностика, из которой
  формируется согласованный с клиентом список работ;
- список работ передаётся мастеру структурно (чекбоксы, минимум свободного
  текста) — так, что его понимает любой мастер, а не только тот, кто принимал;
- есть прайс-лист по видам работ, единый и понятный клиенту и мастеру;
- виден результат: факт против нормы по времени, переделки, загрузка, маржа.

## 2. Пользователи и сценарии

| Роль | Кто | Что делает в системе |
|---|---|---|
| Старший механик | Я | Владеет стандартами и тех. картами, утверждает прайс, проводит ОТК, ведёт сложные работы, смотрит аналитику |
| Линейный мастер | 2 сейчас → 3 | Берёт заказ-наряд, работает по тех. карте, отмечает операции, время, запчасти, отклонения, фото |
| Приёмщик | Отдельный человек или мастер по очереди | Оформляет приёмку: клиент, велосипед, жалоба, осмотр, план работ, смета, срок |
| Клиент | Спортсмены сборных, любители, комьюнити, прохожие | (позже) статус ремонта, согласование доп. работ |
| Руководитель | — | (позже) сводки по выручке и загрузке |

Ключевые сценарии:

1. **Очередь.** Клиент оставляет велосипед → приёмка → работа → ОТК → выдача.
2. **По записи «пока ждёшь».** Предварительная дефектовка по телефону/фото →
   бронь слота и запчастей → клиент приходит в слот → работа в присутствии →
   выдача в тот же визит.
3. **Спортсмен сборной.** Быстрый приоритетный ремонт, полная история по раме,
   зафиксированные моменты затяжки и заменённые детали.

## 3. Границы

**Делаем в v1:**
- Справочник видов работ и технологические карты.
- Прайс-лист по видам работ.
- Приёмка и заказ-наряд.
- Учёт выполнения: операции, время, запчасти, отклонения, фото, ОТК.
- Справочник клиентов (ключ — номер телефона), согласие на обзвон, несколько
  велосипедов на клиента.
- Запись на слоты «пока ждёшь».
- Базовая аналитика: факт/норма, загрузка, переделки.

**Не делаем в v1 (позже):**
- Полноценный складской учёт с закупками и поставщиками (пока лёгкое списание).
- Личный кабинет клиента и онлайн-оплата.
- Интеграция с 1С по API (пока ручной обмен, если нужно).
- Вторая точка в интерфейсе (в модели данных — заложено).
- Отдельный учёт велосипедов по номеру рамы (добавим, если появится потребность).
- Байкфит — отдельная услуга, к мастерской не относится.
- Списки инструмента и оснащения верстаков — отдельный документ о порядке в
  мастерской, не приложение.
- Развёрнутая ветка операций для приводов e-bike (обслуживаем по спросу,
  отдельные карты пока не пишем).

## 4. Архитектурные принципы

1. **Мультиточечность в данных с первого дня.** Каждая сущность привязана к
   точке (`location_id`). Интерфейс пока показывает одну точку.
2. **Клиент — центральная сущность.** Уникальный ключ — номер телефона. У клиента
   может быть несколько велосипедов. Отдельный учёт велосипедов (по номеру рамы)
   на этом этапе не ведём — добавим, если появится потребность.
3. **Тех. карта — единый источник нормы.** Норма времени, инструмент,
   расходники, критерии приёмки берутся из карты; из неё же считается цена.
4. **Заказ-наряд самодостаточен.** Работы задаются чекбоксами из справочника
   операций, свободный текст — по минимуму. Любой мастер понимает наряд без
   устного контекста от того, кто принимал велосипед.
5. **Диагностика делается всегда.** Запрос клиента фиксируется как есть, но
   список работ формирует диагностика (в идеале — самого квалифицированного
   мастера), а не только слова клиента.
6. **Квалификация мастеров — задел на будущее.** Сейчас уровни/допуски не вводим,
   но структура данных позволяет добавить матрицу допусков позже без переделки.
7. **1С — вторичный источник.** Система самодостаточна; из 1С при необходимости
   подтягиваются клиенты и остатки запчастей, обратно уходят данные для
   бухгалтерии. Не блокируемся на 1С.
8. **Веб на Vercel, mobile-first, без офлайна.** Next.js App Router. Основной
   сценарий — мастер с телефоном у стойки.
9. **Всё фиксируется по факту.** Время — таймером, а не «на глаз». Отклонения от
   карты — обязательное поле.

## 5. Модули и дорожная карта

| Фаза | Модуль | Результат |
|---|---|---|
| 0 | Справочник видов работ + шаблон тех. карты | `work-taxonomy.md`, `tech-card-template.md` |
| 1 | Технологические карты на топ-операции (80% потока) | 15–20 заполненных карт |
| 2 | Прайс-лист | Цены по видам работ, пакеты ТО |
| 3 | Процесс приёмки на бумаге/в чек-листе | Обкатанная форма приёмки |
| 3.5 | Консольный прототип рабочего процесса | `console-app.md` — весь поток + раннер процедур + автотесты; ядро на TS переиспользуется в вебе |
| 4 | Веб-приложение MVP | ✅ Next.js: обращения (генерация номеров), диагностика DIA-01 с чек-листами и списком неисправностей, оценка стоимости с вилкой по трудностям, согласование, ремонт по процедурам, повторная диагностика, выдача. Прайс-лист правится в приложении. Хранение — localStorage |
| 5 | Оснащение рабочих мест | Отдельный документ: списки инструмента на верстаках (вне приложения) |
| 6 | Запись на слоты «пока ждёшь» | Календарь слотов + предварительная дефектовка |
| 7 | Аналитика и матрица допусков | Отчёты, допуски мастеров по операциям |
| 8 | Пошаговый мастер ремонта в приложении | Алгоритмы из `procedures/` как интерактивный гид (режимы детализации) |

Порядок фаз 0–3 жёсткий (стандарт до приложения). Фазы 4–8 можно тасовать.

## 6. Журнал ключевых решений

| # | Решение | Причина |
|---|---|---|
| 1 | Стандартизация (тех. карты, прайс, приёмка) — до приложения | Приложение оцифровывает процесс, а не создаёт его |
| 2 | Клиент опознаётся по телефону. Велосипед и обращение получают сгенерированные номера (`B-…`, `V…`); в обращение пишется велосипед, запчасти, кто работал, стоимость. QR/штрих-код на наклейке — этап веба | Нужна прослеживаемость по обращению, но без VIN |
| 3 | `location_id` во всех сущностях с первого дня | Вторая точка в середине следующего сезона |
| 4 | Инструмент и рабочие места — вопрос порядка в мастерской, не приложения; ведём как простые списки «что на верстаке» | Приложение это не отслеживает |
| 5 | Норма времени из тех. карты используется и для цены, и для длины слота | Единый источник, меньше рассинхрона |
| 6 | E-bike обслуживаем без акцента; отдельные операции и карты пока не разворачиваем | Приоритет — шоссе / гревел / МТБ |
| 7 | Байкфит вынесен из системы мастерской | Отдельная услуга |
| 8 | Уровни квалификации / допуски мастеров сейчас не вводим, но закладываем в модель данных | Пока команда маленькая; апгрейд нужен при росте |
| 9 | Список работ мастеру — структурно (чекбоксы из справочника), свободный текст минимизируем | Наряд должен быть понятен любому мастеру вне контекста |
| 10 | Повторная диагностика после ремонта обязательна (тот же чек-лист + моменты затяжки) | Контроль качества перед выдачей |
| 11 | Тела процедур пишем по Park Tool (BBB-4, Repair Help, YouTube), при необходимости — дилерские мануалы; ссылки прикрепляем | Не изобретать с нуля; формализация и связка с системой — наша часть |
| 12 | Алгоритмы ремонта встраиваются в приложение как пошаговый мастер с регулируемой детализацией (модель Photomath): режимы «Мастер / Стандарт / Обучение», листание по главам | У мастеров разный уровень, а софт один |

## 7. Открытые вопросы

1. **Ставка нормо-часа** — единая на все работы или выше за сложные? Известна ли
   текущая цифра?
2. **Приёмка** — отдельный приёмщик всегда, или мастера по очереди?
3. **Обмен с 1С** — что именно и в какую сторону нужно (клиенты? остатки?
   выручка?).
