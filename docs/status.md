# Текущее состояние проекта — сводка для новой сессии

Обновлено: 2026-09-11 · последний коммит `main`: `2e52a3b`

## Что это

Веломастерская Veloterra (топовая точка, дальше вторая точка). Строим систему
работы: технологические карты ремонта → приложение, которое ведёт мастера по
шагам, считает диагностику и цены, хранит обращения. Полная концепция —
`docs/vision.md`.

## Что уже готово

- **Документация мастерской** (`docs/`): справочник видов работ
  (`work-taxonomy.md`), процесс приёмки (`intake-flow.md`), шаблон тех. карты,
  спецификация консоли (`console-app.md`).
- **Каталог процедур** (`catalog/*.proc`) — **58 техпроцедур** по всем узлам
  (трансмиссия, тормоза, колёса, втулки, рулевая, каретка, рама, электроника,
  мойка) в собственном текстовом формате (см. `src/dsl.ts` — грамматика).
  Плюс `catalog/faults.json` (типовые неисправности по узлам) и
  `catalog/prices.json` (цены работ + трудности с надбавками).
- **Движок процедур** (`src/runner.ts`, порт в `web/runner.js`) — ведёт
  исполнителя по шагам, ветвлениям, циклам, вложенным вызовам между
  процедурами; 3 режима детализации (Мастер / Стандарт / Обучение).
- **Проверки каталога**: `npm run check` = validate + dryrun (головной прогон
  каждой процедуры по всем веткам) + audit (эвристики на дыры в формулировках).
  Сейчас — 0 ошибок.
- **Консольная версия** (`npm run cli`, `src/*.ts`) — весь рабочий процесс
  текстом в терминале. Рабочая, но это была промежуточная ступень.
- **Веб-приложение** (`web/*.js`, ванильный JS без фреймворков):
  - обращение (клиент по телефону, велосипед с генерируемым номером `B-…`,
    номер обращения `V…`);
  - диагностика — чек-лист по узлам/блокам с режимом «Мастер», при «не норма»
    раскрывается список неисправностей → работы в наряд;
  - оценка стоимости — вилка «от…до» по трудностям (будет / не будет /
    неизвестно), материалы и запчасти отдельной строкой;
  - согласование → ремонт (раннер по процедуре, отметки времени/запчастей) →
    повторная диагностика → выдача;
  - прайс-лист правится в самом приложении.
  - Часть этой логики (диагностика по блокам, вилки цен) дописана параллельной
    сессией с домашней машины (ветка `diagnostics-blocks`) и уже влита в `main`.
- **Сборка** (`scripts/build-html.js`) — обычный Node без пакетов и без
  TypeScript, склеивает `web/*` + `catalog/*` в **один файл**:
  `veloterra.html` (открыть локально) и `public/index.html` (для хостинга).
- **Общее хранилище** (`api/db.js`) — серверная функция на Vercel, данные в
  Upstash Redis, слияние правок с разных устройств вместо перезаписи.
- **Многопользовательский режим** (`api/auth.js`, `api/users.js`, `api/_lib.js`):
  вход по логину/паролю, своя реализация без сторонних сервисов (пароли —
  scrypt, сессия — подписанная HttpOnly-кука на секрете `SESSION_SECRET` из
  переменных окружения Vercel). Первый, кто откроет приложение, создаёт
  единственного администратора («Первый запуск») — дальше только админ через
  «Админка → Мастера» заводит остальных (роль мастер/администратор, смена
  пароля, отключение/удаление; нельзя остаться без единственного админа).
  Каждый пользователь может сменить свой пароль в «Профиль». `/api/db` теперь
  требует авторизацию — без входа приложением пользоваться нельзя.
- **Остатки по запчастям** (`api/stock.js`, «Админка → Остатки»): список
  артикул/название/остаток/единица, правится вручную или вставкой текстом
  (`артикул;название;остаток;единица`, по строке на позицию) — задел под
  будущую выгрузку из 1С, прямой интеграции с 1С пока нет.

## Как выложено

- Репозиторий на GitHub: `TimurSharipov02/bikeshop`, ветка `main`.
- Vercel подключён через GitHub, Import Project завершён, продакшен —
  `https://bikeshop-chi.vercel.app`. Любой пуш в `main` = новый деплой
  (Claude пушит сам, без отдельного запроса на каждый пуш — см. `CLAUDE.md`).
- Upstash for Redis подключён (Storage → бесплатный тариф) и redeploy сделан.
  Главный экран приложения подтверждает: «Данные общие для всех устройств.» —
  обращения теперь видны с любого устройства, а не только в том браузере, где
  их создали.

## Ключевые решения по ходу (см. также `vision.md` §6)

- Стек — **обычный JavaScript, без npm-зависимостей во время работы
  приложения**. npm нужен только чтобы один раз собрать `veloterra.html`
  (`node scripts/build-html.js`, без пакетов). Next.js/React пробовали и
  убрали — пользователь не разработчик, важно, чтобы стек был понятным и
  прозрачным.
- Общие данные — через облако (Vercel + Upstash), не через локальный сервер в
  мастерской: пользователь явно выбрал этот вариант.
- Прайс — вилка «от…до»: цена работы + трудности с состоянием
  будет/не будет/неизвестно, а не фиксированная цифра.
- Пакеты ТО и группа BUILD (сборка велосипедов из коробки) — сознательно
  отложены, не начаты.

## Дальше

1. **Первый шаг пользователя**: открыть `bikeshop-chi.vercel.app` и создать
   администратора на экране «Первый запуск» — это должен сделать он сам
   (пароль вводит только он). До этого приложением пользоваться нельзя.
2. Табель рабочего времени, нагрузка мастеров (число работ/часов, часы на
   месте) и оплата за работу — запрошено пользователем, но сознательно
   отложено как отдельная задача: нужно сперва решить, как считать часы
   (ручной ввод? отметки прихода/ухода?) и как считать оплату (ставка в час?
   сдельно по операциям?), прежде чем проектировать данные.
3. Продолжать наполнять/чистить каталог процедур по замечаниям пользователя
   (он вычитывает шаг за шагом и правит формулировки).
4. Группа BUILD и пакеты ТО — когда дойдут руки.
