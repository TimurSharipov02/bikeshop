# Консольное приложение — прототип рабочего процесса

Статус: черновик · Дата: 2026-09-10

## Зачем

**Главная цель — валидация алгоритмов.** Прогон каждой процедуры вручную через
раннер = и есть проверка: там, где инструкция обрывается, ветка ведёт в тупик,
`ВЫЗОВ` указывает на заглушку, шаг сформулирован неоднозначно или не хватает
варианта — это всплывает при прохождении. По ходу правим прозу в `procedures/`.

Побочно консоль обкатывает весь рабочий процесс мастерской до веба. Консоль —
это «скелет»: тот же поток и та же логика, что в будущем вебе, но без интерфейса.
Ядро (модель данных, раннер процедур, проверки) пишется один раз на
TypeScript / Node и переиспользуется в Next.js на Vercel.

## План валидации

1. Перевести все функции из `procedures/*.md` в структурированный формат.
2. Автопроверки на весь каталог (ссылки, пустые ветки, заглушки, уровни детализации).
3. Пройти раннером **каждую** функцию по **всем** комбинациям параметров.
4. Каждую найденную дыру — записать и исправить в исходном `.md`.
5. Повторять, пока чистый прогон всего каталога.

## Философия

Здесь машина — это «голова», человек — «руки». Не классическая автоматизация
ручного труда, а перенос знаний: опыт старшего механика зашит в алгоритм и ведёт
любого новичка по шагам. Рычаг тот же — просто приложен к знанию, а не к гайке.

## Поток (этапы)

```
1. Приветствие
2. Опросник по состоянию велосипеда  (запуск функции DIA-01)
3. Фиксация неисправностей
4. Согласование с клиентом
5. Фиксация работ  →  формирование заказ-наряда
6. Отправка работ мастеру
7. Ведение мастера по списку работ  (раннер процедур из procedures/)
8. Приёмка  (запуск функции «Повторная диагностика»)
9. Возврат клиенту
```

### 1. Приветствие

Экран-заставка: название, версия, короткая подсказка. Роль не спрашиваем — один
человек может делать всё. Сразу выбор действия: новое обращение / открытые
обращения (по номеру).

### 2. Опросник по состоянию велосипеда

- Ввод клиента: имя, **телефон (уникальный ключ)**, согласие на обзвон.
- Ввод велосипеда: тип (шоссе / гревел / МТБ), бренд, модель.
  - Если велосипед новый для системы → **сгенерировать номер велосипеда**
    (напр. `B-000042`); он остаётся за велосипедом на все визиты.
  - Если известен номер велосипеда → найти его историю.
- **Сгенерировать номер обращения** (напр. `V26-000147`: код точки, год,
  порядковый). Всё дальше пишется в это обращение.
- Запрос клиента — свободным текстом, коротко.
- Запуск функции **DIA-01 «Приёмка — диагностика велосипеда»** из `procedures/intake.md`:
  приложение ведёт по чек-листу, на каждом пункте — отметка «норма / требует
  работы / риск», минимум свободного текста.

### 3. Фиксация неисправностей

На каждой `ПРОВЕРКЕ` диагностики, где ответ «не норма», раскрывается **список
типовых неисправностей своей группы** (`catalog/faults.json`): узлы → колёса,
покрышки, тормоза, трансмиссия, каретка, рулевая, подвеска, рама. Мастер
отмечает нужные пункты (номера через запятую) и пишет комментарий. Каждая
неисправность привязана к операции из каталога → сразу падает в список работ.
Работы можно и добавить вручную — выбором из каталога (поиск по коду/названию
или по группам), без ввода кодов из головы.

### 4. Согласование с клиентом

Показать смету: операции в клиентских названиях + цены из прайса + запчасти +
срок. Отметить, что клиент подтвердил, что отклонил. Зафиксировать «уже было
сломано до нас».

### 5. Фиксация работ → заказ-наряд

Подтверждённые позиции превращаются в **заказ-наряд**: список операций (коды +
названия), по каждой — отметки диагностики. Присвоить номер, статус «в работе».

### 6. Отправка работ мастеру

Наряд уходит выбранному мастеру. Мастер видит только структурный список —
понятный без устного контекста.

### 7. Ведение мастера по списку работ

Для каждой операции наряда — запуск соответствующей **функции из `procedures/`**:

- приложение спрашивает параметры функции (напр. `тип: механика | гидравлика`);
- ведёт по главам и шагам;
- на `ВЫЗОВ` заходит в подпроцедуру и возвращается;
- показывает `ПРОВЕРИТЬ` как контрольные точки;
- поддерживает режимы **Мастер / Стандарт / Обучение** и пропуск глав;
- мастер отмечает: выполнено, фактическое время (таймер), израсходованные
  запчасти, отклонения от карты;
- найденные доп. работы → возврат к этапу 4 (согласование).

### 8. Приёмка

Запуск функции **«Повторная диагностика (после ремонта)»**: тот же чек-лист +
моменты затяжки + проверка критериев приёмки всех операций + тест-райд.

### 9. Возврат клиенту

Итог: перечень выполненного, потраченное время, запчасти. Смена статуса заказа
на «выдан». Данные клиента остаются для обзвона.

## Что нужно от процедур

Функции из `procedures/*.md` (проза) переводятся в структурированный формат —
один файл на функцию: главы → шаги → под-шаги, узлы ветвления, ссылки `ВЫЗОВ`,
параметры, чекпойнты, уровень детализации у каждого узла. Этот формат и грузит
приложение.

## Модель данных (эскиз)

- `Client` — id (телефон), имя, согласие на обзвон, `location_id`.
- `Bike` — **сгенерированный номер** (`B-000042`), тип, бренд, модель; текущий
  владелец (клиент); история обращений.
- `WorkOrder` (обращение) — **сгенерированный номер** (`V26-000147`), клиент,
  велосипед, запрос, статус, `location_id`, даты (приём / готово / выдан),
  итоговая стоимость для клиента.
- `WorkItem` — код операции, название, отметки диагностики (риски, запчасти),
  согласование (да / нет), факт (время, запчасти, отклонения), статус,
  кто выполнял.
- `PartUsed` — запчасть / расходник, количество, к какому `WorkItem`, цена.
- `Person` — кто работал с велосипедом (в консоли — просто имя из списка).
- `ProcedureRun` — какая функция, значения параметров, позиция (глава/шаг),
  режим детализации, журнал отметок.

Номер обращения и номер велосипеда на этапе веба кодируются в штрих/QR-код,
печатаются на наклейке и клеятся на велосипед. В консоли — просто вводятся
и ищутся по номеру.

## Автотесты (на этапе консоли)

- каждая ссылка `[XXX-NN]` в процедурах резолвится в существующую функцию;
- нет главы / ветки без шагов;
- `ВЫЗОВ` не ведёт в заглушку без явной пометки;
- фильтр по уровню детализации даёт непустой вывод во всех режимах;
- прогон каждой функции по всем комбинациям параметров завершается без тупика.

## Стек

- TypeScript + Node, запуск через `tsx` / `node`.
- Ядро (`core/`): типы модели, загрузчик процедур, раннер, валидатор — без вывода.
- Консольная оболочка (`cli/`): ввод-вывод, меню, промпты.
- Хранилище на этапе консоли — JSON-файлы на диске.
- Веб потом: Next.js App Router на Vercel, тот же `core/`.
